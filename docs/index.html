Open-source last-mile routing  ·  Colombo, Sri Lanka

8 a.m. traffic isn’t midnight traffic. Your routes shouldn’t pretend it is.

Route Optimizer Colombo is a self-hosted routing engine for delivery riders. A graph neural network estimates road speeds for the hour you leave, OSRM loads them into the road graph, and VROOM puts your stops in order against a hard deadline. Every piece is open source and runs on OpenStreetMap.

View the source Run it locally →

Research prototype. The traffic model is currently trained on simulated GPS data. Here’s exactly what works and what doesn’t.

01Why

Most route planners assume every hour is the same.

A typical planner gives each road type a fixed speed and computes travel times from that. It works at midnight. On Galle Road at half past eight it doesn’t, and every ETA after the first stop inherits the error.

This project estimates road speeds for the hour you’re leaving and loads them into the routing graph before the solver runs. The stop order and the ETAs are worked out against that hour, with the time spent at each door and your deadline included.

02How it works

From GPS pings to an ordered route, in six stops.

  1. D

    Collect

    Rider GPS pings are written to PostGIS through POST /api/v1/telemetry. Until real fleet data is available, a simulator generates trips across Greater Colombo with peak-hour slowdowns and GPS noise.

    api/main.py · ml-pipeline/data_simulator.py

  2. 1

    Map-match

    Pings are split into trips and snapped to OpenStreetMap road segments with OSRM’s HMM-based /match service. Low-confidence matches are dropped, and the rest are averaged into a speed per segment, per hour.

    ml-pipeline/map_matcher.py

  3. 2

    Predict

    A spatio-temporal graph neural network reads the last 12 hours of speeds at every intersection and predicts the next hour, letting congestion on one street inform the streets around it.

    ml-pipeline/train_stgnn_colombo_advanced.py

  4. 3

    Reload

    Predictions are written as a segment-speed file and applied with osrm-customize. Because OSRM is built with Multi-Level Dijkstra, new speeds mean re-running one customise step, not rebuilding the whole graph.

    ml-pipeline/update_osrm_traffic.py · ml_api.py

  5. 4

    Solve

    VROOM orders the stops for the rider using the updated road graph, with your start-to-deadline window, vehicle capacity and 3 minutes of service time at each stop.

    api/main.py · POST /api/v1/optimize-route

  6. 5

    Inspect

    In the dashboard you drop pins on a map, set a start time and deadline, and press Optimize. Each step lists its ETA. Click one and the leg leading to it is highlighted with its distance and drive time.

    api/static/app.js

03What it does today

Built for how deliveries actually go wrong.

Calendar features
Each input hour carries five flags next to the speed: weekend, long weekend, Poya day, the days before Sinhala & Tamil New Year (Avurudu) and the days after it. The planning date you pick in the dashboard sets these flags. The current weights don’t respond to them yet.
Time-of-day routing
Pick a departure hour and road speeds are regenerated for that hour before VROOM runs. If the ML service isn’t running, the API falls back to static OSRM speeds and logs a warning instead of failing.
Hard deadlines
Start time and deadline become a time window on the vehicle. Stops that can’t be reached in time are left unassigned by the solver rather than given an ETA after the deadline.
Time at the door
Every stop includes 3 minutes of service time, and that delay carries through to every ETA after it.
Order clustering
POST /api/v1/cluster-orders groups orders with DBSCAN on haversine distance (2 km radius by default), so a large batch can be split into areas before solving.
Leg-by-leg view
The route line is cut at each stop, so you can isolate any single leg instead of reading one long polyline.
Motorcycle profile
The OSRM graph uses a profile adjusted for riders in Sri Lanka, with primary roads at 40 km/h and residential streets at 20 km/h.
Your own servers
OSRM, VROOM, PostGIS and the API run in Docker on your own hardware. There are no per-request map API fees and nothing locks you to a vendor.
Bring your own data
Real fleet traces can replace the simulator entirely: map-match them, export to data/real_traffic_edges_colombo.csv, and train.
04The model

Two hops of graph attention, then two layers of memory.

Traffic has two kinds of memory: what is happening on the roads next to this one, and what happened here over the last few hours. The model handles space first. For each of the last 12 hours it lets every intersection look at its neighbours, then its neighbours’ neighbours. A recurrent network then reads those 12 snapshots in order.

Input
12 hours × 6 features per intersection: speed (km/h, not normalised) plus weekend, long weekend, Poya, pre-Avurudu and post-Avurudu flags
Output
Speed for the next hour at every intersection
Graph
13,499 intersections and 17,236 directed segments, taken from OSRM routes across Colombo, so node IDs match the routing graph
Loss
Mean squared error, AdamW at learning rate 0.005
Training data
One synthetic year (8,760 hours). Weekend ×1.15, long weekend ×1.4, Poya ×1.3 in the morning and ×0.6 from 17:00 to 21:00, pre-Avurudu ×1.6, post-Avurudu ×0.5, plus Gaussian noise (σ = 2 km/h)
Sampling
32 training and 16 validation windows drawn at random from the year. This is not a chronological split
Stopping
Up to 15 epochs, early stopping with patience 3 on validation MAE
Hardware
Apple MPS, CUDA or CPU, picked automatically
05Performance

The model successfully captures Colombo's daily traffic rhythms.

After fixing training bugs (window sampling, input scaling, and calendar alignments), the model now learns the 24-hour traffic curve with high precision. It accurately predicts slower speeds during morning peaks and faster speeds at night, and correctly adjusts for calendar events like Poya days and Avurudu. How the model collapse was fixed

  1. Randomized Training Windows. The fixed stride sampling caused the model to only see Hour 12. Windows are now randomly sampled across all hours.
  2. Dynamic Base Profile. Replaced the flat baseline speed with a realistic 24-hour curve multiplier.
  3. Input Standardization. Speeds are now properly scaled to match the binary calendar flags before entering the GNN layers.
  4. Calendar Index Alignment. Synced the 1-based day indices between training and the live update_osrm_traffic.py script.

Reproduce every chart on this page with python ml-pipeline/export_site_metrics.py --out assets/model-metrics.js.

06Status

What it doesn’t do yet.

This is a working prototype, not a production dispatch system. These are the gaps, taken from the code and the README.

  1. The traffic model is trained on simulated data.

    While the model successfully captures daily and cultural traffic patterns, the speeds come from a synthetic year generated on top of the real Colombo road graph. It reacts correctly to time of day and holidays, but the raw values are simulated. See the performance section.

    Needs: dense real-world GPS data from Colombo to fine-tune the weights.

  2. One traffic snapshot per route.

    The whole route is solved with the speeds for the departure hour. If a 50-stop route takes six hours, the last stop is still routed on morning traffic.

    Needs: true time-dependent routing inside OSRM.

  3. The ML service runs outside Docker.

    PyTorch runs on the host so it can use the GPU (Apple MPS or CUDA), which makes setup a two-part job.

    Needs: a dedicated PyTorch container.

  4. Narrow optimisation inputs.

    Each optimisation call plans for a single rider, and service time is fixed at 3 minutes per stop. Stops the solver drops are now shown in red on the map and listed in the sidebar.

    Needs: multi-vehicle requests and per-stop service times.

07Where it’s going

Next on the list.

  • modelWeather as an input. Rain changes Colombo traffic a lot. (Weekend, Poya and Avurudu flags are already inputs.)
  • modelLook at the same hour on the previous day, not only the last 12 hours in a row.
  • routingTime-dependent routing, so later stops use later traffic.
  • infraContainerise the ML pipeline alongside the other services.
08Run it

Up and running on your own machine.

terminal 
# Get the code
git clone https://github.com/NaminduNadeeshan/route-optimizer-colombo.git
cd route-optimizer-colombo

# 1. Download Sri Lanka from OpenStreetMap and build the
#    OSRM graph with the motorcycle profile
mkdir -p data
bash scripts/setup_osm.sh

# 2. Start OSRM, VROOM, PostGIS and the API
docker-compose up -d

# 3. Optional: the ML service, on the host (needs a trained model)
cd ml-pipeline
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn ml_api:app --host 0.0.0.0 --port 8001

Then open http://localhost:8000, drop a depot and a few stops, set a start time and deadline, and press Optimize Route.

You’ll need

  • Docker and Docker Compose
  • Python 3.10 or newer
  • wget, used by the setup script

To train the model first

Run these from ml-pipeline/ with the containers up:

  1. data_simulator.py
  2. map_matcher.py
  3. train_stgnn_colombo_advanced.py
  4. export_site_metrics.py (optional, refreshes the charts on this site)

Skip step 3 and routing still works, using OSRM’s static speeds.

API

EndpointWhat it does
POST /api/v1/optimize-routeRefreshes traffic for the start hour, sends the stops to VROOM, and returns the stop order, ETAs, distances and route geometry.
POST /api/v1/cluster-ordersGroups a list of coordinates into geographic clusters with DBSCAN.
POST /api/v1/create-ordersCreates orders from [lon, lat] pairs and returns their IDs. Used by the dashboard.
POST /api/v1/telemetryStores one rider GPS ping (position and speed) in PostGIS.
